# Техническое задание: MedBook API — онлайн-запись к врачам

**Уровень:** Средний  
**Стек:** Python 3.11+, FastAPI, Pydantic v2, Uvicorn  
**Хранение данных:** исключительно в памяти Python (`list[dict]`, `dict[int, dict]` и т. п.)  
**База данных, ORM и авторизация:** не используются

## 1. Цель проекта

Разработать REST API для управления пациентами, врачами, медицинскими специализациями и записями на приём. Проект должен закрепить знания FastAPI, Pydantic, CRUD, `APIRouter`, связей между сущностями через ID, фильтрации и бизнес-валидации.

> Это учебный API, не предназначенный для хранения реальных медицинских данных. Все записи теряются после перезапуска приложения. При нескольких процессах сервера их хранилища не синхронизируются.

## 2. Основные сущности

Студентам необходимо самостоятельно определить Pydantic-схемы для создания, обновления и чтения данных. Ниже перечислены **минимально обязательные** поля; можно добавить дополнительные разумные поля.

### 2.1. `Specialization` — специализация

| Поле | Тип | Требование |
|---|---|---|
| `id` | `int` | Уникальный положительный идентификатор, назначается сервером |
| `name` | `str` | Обязательное, 2–100 символов, уникальное без учёта регистра |
| `description` | `str \| None` | Необязательное описание |

Примеры: кардиолог, терапевт, невролог.

### 2.2. `Doctor` — врач

| Поле | Тип | Требование |
|---|---|---|
| `id` | `int` | Назначается сервером |
| `full_name` | `str` | Обязательное, 3–100 символов |
| `specialization_id` | `int` | ID существующей специализации |
| `experience_years` | `int` | Неотрицательное число |
| `consultation_price` | `float` | Число больше нуля |
| `is_active` | `bool` | Доступен ли врач для новых записей, по умолчанию `true` |

### 2.3. `Patient` — пациент

| Поле | Тип | Требование |
|---|---|---|
| `id` | `int` | Назначается сервером |
| `full_name` | `str` | Обязательное, 3–100 символов |
| `phone` | `str` | Обязательный контактный номер, непустой |
| `email` | `EmailStr \| None` | Необязательный корректный email |
| `birth_date` | `date \| None` | Дата рождения не в будущем |

Не хранить настоящие персональные или медицинские данные в учебном проекте.

### 2.4. `Appointment` — запись на приём

| Поле | Тип | Требование |
|---|---|---|
| `id` | `int` | Назначается сервером |
| `patient_id` | `int` | ID существующего пациента |
| `doctor_id` | `int` | ID существующего врача |
| `start_at` | `datetime` | Дата и время начала приёма в будущем |
| `duration_minutes` | `int` | Длительность: 15, 30, 45 или 60 минут |
| `status` | `str / Enum` | `scheduled`, `completed`, `cancelled` |
| `reason` | `str \| None` | Необязательное краткое описание цели визита |

**Рекомендация:** все даты и время хранить как timezone-aware `datetime` в UTC; в запросах использовать ISO 8601 с указанием смещения, например `2026-12-01T09:00:00+05:00`.

## 3. Связи между сущностями

```text
Specialization (1) ────── (N) Doctor
Doctor         (1) ────── (N) Appointment
Patient        (1) ────── (N) Appointment
```

- У каждого врача есть одна специализация.
- У одной специализации может быть несколько врачей.
- У пациента может быть много записей к разным врачам.
- У врача может быть много записей в разное время.
- Связи поддерживаются вручную через `*_id`, без внешних ключей БД.

## 4. API-эндпоинты

Базовый префикс всех маршрутов: `/api/v1`.

### 4.1. Специализации — 5 эндпоинтов

| Метод | URL | Действие |
|---|---|---|
| `POST` | `/specializations` | Создать специализацию |

| `PATCH` | `/specializations/{specialization_id}` | Частично изменить специализацию |
| `DELETE` | `/specializations/{specialization_id}` | Удалить специализацию |

### 4.2. Врачи — 6 эндпоинтов

| Метод | URL | Действие |
|---|---|---|

| `GET` | `/doctors` | Получить врачей с фильтрами |
| `GET` | `/doctors/{doctor_id}` | Получить врача по ID |
| `PUT` | `/doctors/{doctor_id}` | Полностью обновить врача |
| `PATCH` | `/doctors/{doctor_id}` | Частично обновить врача |
| `DELETE` | `/doctors/{doctor_id}` | Удалить врача |

**Фильтры для `GET /doctors`:** `specialization_id`, `is_active`, `min_experience`, `max_price`; дополнительно — поиск по имени `search`.

### 4.3. Пациенты — 6 эндпоинтов

| Метод | URL | Действие |
|---|---|---|

| `GET` | `/patients` | Получить список пациентов |
| `GET` | `/patients/{patient_id}` | Получить пациента по ID |
| `PUT` | `/patients/{patient_id}` | Полностью обновить пациента |
| `PATCH` | `/patients/{patient_id}` | Частично обновить пациента |

### 4.4. Записи на приём — 8 эндпоинтов

| Метод | URL | Действие |
|---|---|---|
| `POST` | `/appointments` | Записать пациента к врачу |
| `GET` | `/appointments` | Получить все записи с фильтрами |
| `GET` | `/appointments/{appointment_id}` | Получить запись по ID |
| `PATCH` | `/appointments/{appointment_id}` | Изменить время, врача или длительность записи по правилам проверки |

**Фильтры для `GET /appointments`:** `doctor_id`, `patient_id`, `status`, `date` (формат `YYYY-MM-DD`).

**Итого: 25 обязательных эндпоинтов.**

## 5. Бизнес-правила

### 5.1. Создание записи

При `POST /appointments` необходимо проверить:

1. Пациент существует.
2. Врач существует и `is_active == true`.
3. Начало приёма находится в будущем.
4. Длительность принадлежит разрешённому набору.
5. У врача нет другой **активной записи со статусом `scheduled`**, которая пересекается по времени.
6. Если проверки успешны, создать запись со статусом `scheduled`.

**Правило пересечения интервалов:** две записи пересекаются, когда

```text
new_start < existing_end AND existing_start < new_end
```

Пример: у врача есть приём с 10:00 до 10:30. Новая запись на 10:15–10:45 недопустима, а на 10:30–11:00 допустима.

### 5.2. Изменение записи

- При изменении врача, времени или длительности повторно проверять занятость.
- Не учитывать саму редактируемую запись при поиске конфликтов.
- Изменять время и врача можно только у записи со статусом `scheduled`.
- Нельзя менять `status` произвольно через общий `PATCH`; для переходов использовать специальные маршруты.

### 5.3. Отмена и завершение

- `scheduled → cancelled` — допустимо.
- `scheduled → completed` — допустимо только после окончания приёма.
- Повторная отмена, завершение отменённой записи и изменение завершённой записи — ошибка.
- Отменённые записи остаются в истории, но не блокируют время врача.
- Завершённые записи также остаются в истории.

### 5.4. Удаление связанных данных

Чтобы не оставлять «висячие» ID:

- Запретить удаление специализации, если к ней привязан хотя бы один врач.
- Запретить удаление врача, если у него есть хотя бы одна запись (включая отменённую и завершённую).
- Запретить удаление пациента, если у него есть хотя бы одна запись.
- Для каждого запрета возвращать `409 Conflict` с понятным сообщением.

## 6. Pydantic: обязательные требования

- Использовать Pydantic **v2** и `BaseModel`.
- Создать отдельные схемы `...Create`, `...Update`, `...Response` для сущностей; для врачей и пациентов также предусмотреть схему полного обновления (`...Replace`) либо аналог.
- `id` генерируется сервером и не принимается в теле создания.
- Применять `Field()` для ограничений и `EmailStr` для email.
- Использовать `Enum` или `Literal` для статусов.
- Применять `field_validator` / `model_validator`, когда простого `Field()` недостаточно.
- При `PATCH` обновлять **только переданные поля** (`model_dump(exclude_unset=True)`), сохраняя остальные значения.
- Не позволять передавать неизвестные поля в схемах изменения (`extra='forbid'` — рекомендовано).
- Использовать `response_model` для API-ответов.

## 7. Хранение данных без БД

Для каждой сущности предусмотреть отдельную коллекцию в памяти. Например:

```python
specializations = []
doctors = []
patients = []
appointments = []
```

Можно использовать и словари по ID — студент выбирает самостоятельно.

**Обязательно:**

- Не допускать повторного использования ID после удаления элемента.
- Не смешивать данные разных сущностей.
- При обновлении изменять существующий объект, а не добавлять дубликат.
- Реализовать проверку существования связанных ID.
- Понимать, что данные исчезнут после перезапуска приложения.

Запускать учебный API в **одном процессе** без нескольких worker-процессов. Это учебный вариант без гарантий конкурентной записи.

## 8. Примеры запросов

### Создание специализации

`POST /api/v1/specializations`

```json
{
  "name": "Кардиолог",
  "description": "Заболевания сердца и сосудов"
}
```

### Создание врача

`POST /api/v1/doctors`

```json
{
  "full_name": "Фирдавс Саидов",
  "specialization_id": 1,
  "experience_years": 8,
  "consultation_price": 150.0,
  "is_active": true
}
```

### Создание пациента

`POST /api/v1/patients`

```json
{
  "full_name": "Мухаммад Алиев",
  "phone": "+992900001122",
  "email": "patient@example.com",
  "birth_date": "2002-05-12"
}
```

### Создание записи

`POST /api/v1/appointments`

```json
{
  "patient_id": 1,
  "doctor_id": 1,
  "start_at": "2026-12-01T10:00:00+05:00",
  "duration_minutes": 30,
  "reason": "Первичная консультация"
}
```

Успешный ответ содержит созданный объект с серверным `id` и статусом `scheduled`.

### Отмена записи

`PATCH /api/v1/appointments/1/cancel`

Тело запроса не требуется. Запись получает статус `cancelled`.

### Поиск врачей

`GET /api/v1/doctors?specialization_id=1&is_active=true&max_price=200`

### Записи врача за дату

`GET /api/v1/appointments?doctor_id=1&date=2026-12-01`

## 9. HTTP-статусы и ошибки

| Код | Когда использовать |
|---|---|
| `200 OK` | Получение и изменение данных |
| `201 Created` | Создание сущности |
| `204 No Content` | Успешное удаление |
| `404 Not Found` | Сущность по ID не найдена |
| `409 Conflict` | Время занято, повторное/недопустимое изменение статуса или нарушение связей |
| `422 Unprocessable Entity` | Неверные типы, обязательные поля или ограничения Pydantic |

Все ошибки должны иметь понятное сообщение (`HTTPException(detail=...)`).
